## Concrete reader-interface implications

An interface over these sources should present the original prose and exact formal type first, then the relation between them. For each relationship, show its kind (kernel dependency, configured comparison, or curated prose-to-type correspondence), the relevant source edition and review scope. A proof being accepted cannot automatically upgrade a model mapping or a nearby ordinary argument. The already supplied semantic-control example offers a compact demonstration of this limitation.

A reader should be able to select one question, such as “Does the same circuit serve both bounds?” or “What randomness does this direct-product statement quantify over?”, inspect the relevant clauses, then see the existing ordinary bridge if one is required. The interface need not display run chronology, all candidate mappings or the full dependency closure by default. Those are inspection destinations, not introductory content. These are recommendations only; no reader interface was implemented or evaluated in this review.
